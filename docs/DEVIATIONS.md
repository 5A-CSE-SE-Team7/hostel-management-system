# Deviations from the submitted SRS, SAD, and STP

This register records implementation choices and gaps that differ from, or are not fully specified by, the submitted documents. The requirement identifiers below are used as written in the repository; the source documents contain some inconsistent identifiers.

| Area | What differs or is unspecified | Why | Impact / follow-up |
| --- | --- | --- | --- |
| Authentication sessions | Sessions are persisted in a MySQL `sessions` table through `express-mysql-session`; the SRS requires session-based authentication without naming a store. | Durable server-side sessions support logout and role changes across server restarts. | Session data is shared through the configured database. No functional change to user sign-in. |
| API surface | The SAD documents six sample API endpoints; the implementation exposes additional REST/JSON endpoints for the listed use cases. | Each use case needs endpoints for its UI and role workflows. | Keep endpoint behavior and access rules covered by route tests and the API documentation. |
| Workflow statuses | Allocation uses `allocated`, `checked_in`, `checked_out`, and `transferred`; complaints use `submitted`, `assigned`, `in_progress`, and `resolved`; visitors use `pending`, `approved`, `rejected`, and `completed`. These complete status sets are not enumerated in the SRS. | The states represent the implemented workflow transitions. | UI labels and transition rules must stay aligned with these values. Complaints do not have a separate `closed` status. |
| Staff account creation | Public registration creates student accounts only. An administrator creates warden, maintenance, and administrator accounts. The SRS does not specify how staff accounts are provisioned. | Prevents public self-assignment of privileged roles. | The first administrator is created by the seed process; production provisioning must be handled securely. |
| Role permissions | Wardens may edit permitted student profile fields, while only administrators may manage roles. Administrators also receive warden permissions. | This follows the role descriptions and UML use cases in the submitted documents. | Explain the permission mapping during review; server middleware remains authoritative. |
| Complaint attachments | Complaint attachment details are stored as a reference string; the app does not upload or store files. | The SRS describes optional attachment/reference details without specifying file storage. | Users must provide a reference rather than upload a file. |
| Leave and visitor policy | Rejected leave requests require remarks; approval remarks are optional. Student-created visitor records start as `pending`, while staff-created records default to `approved`. | These are policy choices left open by the SAD. | Confirm the choices with the team/course staff before production use. |
| Fee balances | Payments are not rejected solely because they exceed the outstanding balance. | The SRS excludes payment-gateway processing; no submitted HMS rule forbids ledger overpayments. This remains an explicit implementation policy choice. | The ledger can record an overpayment; reconciliation policy remains a product decision. |
| Notifications | In-app notifications are persisted. Email is optional and only sent when SMTP settings are configured. | The submitted documents do not mandate an email provider. | Without SMTP configuration, users still see in-app notifications but receive no email. |
| Runtime and database evidence | The project was initially exercised against MariaDB 10.11; CI is configured for MySQL 8.0. | Local and CI environments differ. | Review CI results for MySQL-specific issues before merge; this checkout has not captured a separate compatibility report. |
| Accessibility evidence (HMS-NF-005) | The integrated branch now includes real-session/MySQL journeys across accounts, bed allocation, complaints and maintenance resolution, plus real role-page axe/overflow scans at 375/768/1280 px. Earlier M1-only simulated checks are retained as component scenarios. Chromium and Firefox CI passed ten scenarios; branded Chrome is configured for the final CI run. Manual screen-reader acceptance remains pending. | Automated scans cover the integrated modules; they do not substitute for manual assistive-technology evaluation. | Review the Chrome/Firefox CI results and complete the screen-reader pass. Do not claim full-system WCAG 2.1 AA conformance until all module pages are audited and findings are resolved. |
| TLS evidence (HMS-SR-001) | Production always enforces HTTPS; direct TLS or an explicitly trusted TLS proxy is supported. Local handshake/proxy guard tests pass, but deployment certificates are not supplied. | Certificates and deployment topology are environment-specific. | Capture TLS configuration and evidence in the deployment environment. |
| Performance, scale, availability, recovery | Local measured benchmarks and failed scalability stress records are retained in the owning branches, and an audited isolated restore was timed at two seconds. A complete deployed month of uptime and production-sized acceptance remain unavailable. | These results depend on the deployed host, data, and monitoring window. | Run and attach the measurements required by HMS-NF-001/002/003/004 before claiming those targets. |
| Source-document identifiers | Some source sections use `HMS-F001..004` or `HMS-SR001`, while the issue index and RTM use hyphenated forms such as `HMS-F-001` and `HMS-SR-001`. The source also contains duplicate acceptance-test and contents entries. | The implementation follows the canonical identifiers used by the backlog and RTM. | Correct the submitted source documents or record the canonical mapping in the RTM. |

## API and reporting clarifications

| Area | What / why | Impact |
|---|---|---|
| SAD sample wire contracts | Existing owner APIs use `email` for login, `id` in allocation creation, and `previousAllocationId`/`allocationId`/`bedId` for transfer. The SAD samples use different field names. Preserve the integrated frontend/API contracts rather than silently break consumers. | Tests and actual route definitions are the implemented wire contract; reconcile the submitted SAD during documentation sign-off. |
| Period reports | Occupancy uses allocation/release history at the selected end date, while historical inventory capacity is returned as unavailable because activation timestamps are not stored; current capacity is reported separately. Check-in/out events are counted by their event dates. | The response states its inventory basis; it does not claim reconstructing historical inventory capacity. Fee dues are an as-of-end balance, not period cash flow. |
| Test-plan authority | The uploaded STP is an ATM sample template, not an HMS-specific executed plan. The HMS plan and execution companion are in `TEST_PLAN.md`, `TEST_EXECUTION.md` and `RTM.md`. | No ATM sample test, policy or metric is treated as an HMS acceptance requirement. Submitted RTMs remain separate from the execution companion. |

## Native bcrypt execution (Sprint 2 scalability)
What: the authentication runtime uses native asynchronous bcrypt while retaining the existing bcrypt-compatible hash format and cost12 policy. Why: real 500-session measurements exposed HTTP event-loop starvation during JavaScript password comparisons. Impact: existing bcryptjs-created hashes remain valid; a native binary is now installed from the locked dependency graph. Tests verify compatibility. This does not by itself satisfy the measured 500-session stress requirement; see HMS-NF-002 verification.
