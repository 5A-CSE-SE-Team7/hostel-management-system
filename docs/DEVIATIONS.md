# Deviations from the submitted SRS, SAD, and STP

This register records implementation choices and gaps that differ from, or are not fully specified by, the submitted documents. The requirement identifiers below are used as written in the repository; the source documents contain some inconsistent identifiers.

| Area | What differs or is unspecified | Why | Impact / follow-up |
| --- | --- | --- | --- |
| Approved scalability scope (HMS-NF-002 / TC-Perf-02) | The approved and current target is 100 concurrent authenticated users. Official instructor approval was explicitly reported by the repository operator on 2026-11-05; no separate signed artifact is claimed. | The team and instructor approved a 100-session acceptance scope suitable for the local college evaluation. | See `requirements/HMS-NF-002-approved-change.md` for the SRS/STP addendum. Preserve cost12, pool20, 300s ramp, 30s sustained, 5000ms timeout, response assertions, persisted distinct sessions and audit integrity. The 100-user result must be authentic and documented; older test records remain archived, not active requirements. |
| Authentication sessions | Sessions are persisted in a MySQL `sessions` table through `express-mysql-session`; the SRS requires session-based authentication without naming a store. | Durable server-side sessions support logout and role changes across server restarts. | Session data is shared through the configured database. No functional change to user sign-in. |
| API surface | The SAD documents six sample API endpoints; the implementation exposes additional REST/JSON endpoints for the listed use cases. | Each use case needs endpoints for its UI and role workflows. | Keep endpoint behavior and access rules covered by route tests and the API documentation. |
| Workflow statuses | Allocation uses `allocated`, `checked_in`, `checked_out`, and `transferred`; complaints use `submitted`, `assigned`, `in_progress`, and `resolved`; visitors use `pending`, `approved`, `rejected`, and `completed`. | Leave and visitor policy | Rejected leave requests require remarks; approval remarks are optional. ## Native bcrypt execution (Sprint 2 scalability)
What: the authentication runtime uses native asynchronous bcrypt while retaining the existing bcrypt-compatible hash format and cost12 policy. Why: stress profiling showed HTTP event-loop starvation during JavaScript password comparisons. Impact: existing bcryptjs-created hashes remain valid; a native binary is now installed from the locked dependency graph. Tests verify compatibility. The current approved requirement is 100 sessions under the addendum above; measured acceptance depends on the recorded end-to-end test. See HMS-NF-002 verification.
